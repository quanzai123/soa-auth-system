Tài Liệu Kỹ Thuật: Hệ Thống Xác Thực Google OAuth 2.0 & Kiến Trúc Bảo Mật JWT

Đặc tả kiến trúc kỹ thuật toàn diện, cơ chế phân tầng bảo vệ với Spring Security 6, quy trình ủy quyền theo chuẩn RFC 6749, mã hóa chữ ký HMAC-SHA384, và các giải pháp chống lỗ hổng bảo mật trong kiến trúc hướng dịch vụ.

Kiến trúc: Service-Oriented Architecture (SOA) • Nền tảng: Spring Boot 4 / Java 21 / Spring Security 6 • Trạng thái: 100% Hoạt động & Đã kiểm thử
1

TỔNG QUAN BÀI TOÁN & GIẢI PHÁP KIẾN TRÚC

Hạn Chế Của Cơ Chế Xác Thực Truyền Thống

  • Nguy cơ rò rỉ dữ liệu (Credential Leak): Việc lưu trữ mật khẩu (dù đã băm) vẫn tiềm ẩn nguy cơ bị tấn công Brute-force hoặc Dictionary Attack khi Database bị xâm nhập.
  • Chi phí hạ tầng và vận hành: Tốn kém tài nguyên cho hệ thống gửi SMS OTP, email xác thực và quy trình khôi phục mật khẩu phức tạp.
  • Rào cản gia nhập (High Friction): Bắt buộc điền thông tin đăng ký dài dòng làm giảm tỷ lệ chuyển đổi của người dùng.

Giải Pháp Federated Identity & Single Sign-On (SSO)

  • Ủy quyền định danh an toàn: Giao phó việc xác thực cho Google Identity Provider; hệ thống hoàn toàn không lưu trữ mật khẩu của người dùng.
  • Xác thực một chạm (Single Sign-On): Tận dụng tài khoản Google có sẵn trên phiên duyệt web của người dùng.
  • Phân quyền tự động theo Tên miền (Domain RBAC): Tự động cấp quyền STUDENT nếu email thuộc miền giáo dục (*.edu.vn, *.edu - như TDTU, Bách Khoa, KHTN...) và PERSONAL cho các tài khoản thông thường còn lại.

Các Mục Tiêu Kỹ Thuật Đạt Được

1. Giải quyết bài toán an toàn thông tin nghiệp vụ: Loại bỏ rủi ro rò rỉ mật khẩu người dùng ở tầng dữ liệu, giảm thiểu chi phí triển khai hệ thống xác thực OTP, và tự động hóa quy trình phân quyền theo domain tổ chức.
2. Tích hợp trong mô hình Microservice / SOA: Hoạt động như một Authentication Gateway: Sử dụng SecurityFilterChain kết hợp với JwtAuthenticationFilter đứng trước các request, phân định rạch ròi tài nguyên Public và Private.
3. Khả năng tương thích và ứng dụng thực tế: Áp dụng tối ưu cho các cổng thông tin sinh viên, hệ thống quản lý học tập (LMS), trang thương mại điện tử, và các ứng dụng phân tán cần cơ chế xác thực tập trung.
4. Khả năng tái sử dụng độc lập (Pluggable Module): Đóng gói thành module độc lập, cung cấp sẵn file Postman Collection (soa-auth-collection.json) và script kiểm thử tự động (test-api-live.sh).

NGUYÊN LÝ GIAO THỨC: OAUTH 2.0 & OPENID CONNECT

Phân biệt OAuth 2.0 (Ủy quyền) và OpenID Connect (Định danh)

OAuth 2.0 (Ủy Quyền - Authorization)

Giao thức cấp quyền truy cập tài nguyên. Trả lời câu hỏi: "Ứng dụng có được quyền truy cập tài nguyên thay mặt người dùng không?" thông qua Access Token.

OpenID Connect (Định Danh - Authentication)

Lớp định danh xây dựng đè lên OAuth 2.0. Trả lời câu hỏi: "Người dùng trước màn hình là ai?" thông qua gói tin id_token (chứa sub, email, name, picture).

Luồng Authorization Code Flow (RFC 6749 Section 4.1)

Google không trả trực tiếp Token về User-Agent nhằm tránh rò rỉ qua Browser History và Referer Header. Thay vào đó, Google trả về mã Authorization Code dùng một lần ($TTL \approx 60 - 120\,\text{s}$). Backend Spring Boot sử dụng mã này kèm theo Client Secret để thực hiện cuộc gọi bí mật (Server-to-Server) tới Google Token Endpoint nhằm nhận Token thật.

Cấu Trúc JSON Web Token (JWT - RFC 7519)

1. Header (Thuật toán)

{"alg": "HS384", "typ": "JWT"}

2. Payload (Claims dữ liệu)

{"sub": "email", "role": "ROLE_USER", "accountType": "STUDENT"}

3. Signature (Chữ ký điện tử)

HMACSHA384(Header.Payload, SecretKey)

* Thuật toán HMAC-SHA384 đảm bảo tính toàn vẹn: Bất kỳ sự thay đổi trái phép nào tại Payload sẽ làm sai lệch chữ ký Signature, khiến yêu cầu bị từ chối ngay lập tức tại tầng bộ lọc.

PHÂN TẦNG BẢO MẬT: PUBLIC VS PRIVATE API

Mọi HTTP request gửi tới hệ thống đều đi qua chuỗi Servlet Filter. Lớp JwtAuthenticationFilter chịu trách nhiệm bóc tách và xác thực Token, còn lớp SecurityConfig thực thi các quy tắc ủy quyền truy cập:

API Endpoint Method Phân loại Header Yêu Cầu HTTP Kỳ Vọng Ý Nghĩa Kỹ Thuật
/api/auth/google/config GET PUBLIC Không cần 200 OK Kiểm tra trạng thái cấu hình Client ID
/api/auth/google/url GET PUBLIC Không cần 200 OK Khởi tạo URL chuyển hướng sang Google OAuth 2.0
/api/auth/google/callback POST PUBLIC Không cần 200 OK Trao đổi Authorization Code lấy Token JWT
/api/users/me (KHÔNG TOKEN) GET PRIVATE Bỏ trống 403 FORBIDDEN Spring Security chặn đứng: Ngắt kết nối tại tầng Filter
/api/users/me (CÓ TOKEN) GET PRIVATE Authorization: Bearer 200 OK Xác thực hợp lệ: Chuyển tiếp vào UserController
/api/auth/logout POST PRIVATE Authorization: Bearer 200 OK Thu hồi Token, nạp vào TokenBlacklistService
/api/users/me (TOKEN ĐÃ LOGOUT) GET PRIVATE Token cũ 403 FORBIDDEN Kiểm chứng Blacklist: Vô hiệu hóa token bị thu hồi
Cơ Chế Chặn Mã HTTP 403 Forbidden

Khi client gửi request GET /api/users/me mà không đính kèm Header Authorization: Lớp JwtAuthenticationFilter không tìm thấy token, do đó bỏ qua việc gán danh tính vào SecurityContextHolder. Kế tiếp, AuthorizationFilter kiểm tra quy tắc .anyRequest().authenticated() và phát hiện context rỗng → Spring Security lập tức kích hoạt Http403ForbiddenEntryPoint và trả về HTTP 403 Forbidden ngay tại tầng Filter. Gói tin hoàn toàn không được dispatch tới UserController.

CƠ CHẾ BẢO MẬT NÂNG CAO ĐÃ HIỆN THỰC

Thu Hồi Token Bằng Blacklist (Logout)

JWT mang tính chất Stateless, server không thể can thiệp trực tiếp vào storage phía Client. Để xử lý bài toán Logout an toàn, hệ thống triển khai TokenBlacklistService sử dụng cấu trúc bảng băm đồng thời ConcurrentHashMap với độ phức tạp tra cứu $O(1)$. Khi người dùng logout, token được nạp vào Blacklist kèm hạn sống ($TTL$). Mọi request tiếp theo sử dụng token này sẽ bị JwtAuthenticationFilter đối chiếu và từ chối với mã HTTP 403.

Ràng Buộc Chống Tài Khoản Mồ Côi (Account Orphan Prevention)

Tài khoản đăng nhập qua Google SSO có thuộc tính passwordHash = null trong Database. Nếu cho phép người dùng hủy liên kết Google tự do, tài khoản sẽ không còn bất kỳ phương thức xác thực nào để đăng nhập lại, dẫn đến tình trạng tài khoản bị cô lập vĩnh viễn. Hệ thống áp dụng ràng buộc an toàn: Bắt buộc phải khởi tạo mật khẩu dự phòng (BCrypt 10 rounds) trước khi thực hiện hủy liên kết Google.

CÂU HỎI KỸ THUẬT THƯỜNG GẶP (TECHNICAL FAQ)

Q1: Cơ chế vô hiệu hóa JWT khi Đăng xuất (Logout) được hiện thực như thế nào trong kiến trúc Stateless?

Hệ thống áp dụng cơ chế Token Blacklist (In-memory ConcurrentHashMap với TTL). Khi người dùng thực hiện POST /api/auth/logout, mã định danh duy nhất (jti) hoặc chuỗi token được ghi vào Blacklist kèm thời điểm hết hạn ($T_{\text{exp}}$). Tại JwtAuthenticationFilter, mỗi request đi qua đều được tra cứu trong Blacklist với độ phức tạp $O(1)$. Nếu token nằm trong Blacklist, bộ lọc lập tức từ chối với mã HTTP 403 Forbidden.

Q2: Tại sao hệ thống bắt buộc phải tạo mật khẩu dự phòng trước khi hủy liên kết Google?

Đây là ràng buộc toàn vẹn bảo mật chống hiện tượng Tài khoản Mồ côi (Account Orphan Prevention). Khi người dùng đăng ký qua Google SSO, trường passwordHash trong cơ sở dữ liệu có giá trị null. Nếu cho phép xóa liên kết Google tự do, tài khoản sẽ không còn bất kỳ phương thức xác thực nào khác để đăng nhập lại. Việc cưỡng chế tạo mật khẩu trước đảm bảo số lượng phương thức xác thực hợp lệ luôn $\ge 1$.

Q3: Mã phản hồi HTTP 403 Forbidden khi thiếu Token được trả về từ tầng nào?

Mã 403 được kích hoạt bởi Spring Security Filter Chain (cụ thể là AuthorizationFilter kết hợp Http403ForbiddenEntryPoint) ngay tại tầng Servlet Filter. Khi request thiếu Header Authorization: Bearer, Authentication trong SecurityContextHolder là null, bộ lọc lập tức ngắt kết nối và trả về 403 mà không bao giờ dispatch request tới UserController.

Q4: Làm thế nào để các microservice viết bằng ngôn ngữ khác (FastAPI, Node.js) cùng xác thực Token này?

Do JWT tuân thủ chuẩn mở quốc tế RFC 7519, các microservice độc lập (Python, Node.js, Go) chỉ cần nạp cùng chuỗi khóa bí mật SecretKey và sử dụng thư viện chuẩn (PyJWT, jsonwebtoken) để thẩm định chữ ký HMAC-SHA384 và trích xuất Claims (sub, role, accountType) mà không cần tạo liên kết phụ thuộc hay truy vấn ngược về cơ sở dữ liệu của Auth Service.
